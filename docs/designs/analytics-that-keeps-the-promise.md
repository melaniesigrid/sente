## Problem Statement

## Demand Evidence

Verbatim, asked which decision she was blocked on:

The consumer of this feature is a hiring manager, not a Joseki player. That is real demand, recurring and specific to a situation she is actually in. It is a credibility need, not a product need.

The second opinion caught something in that sentence that the lead advisor missed: it names **two** interview questions, not one.

1. "Do you have users, how many" — answer not in her control at n=1.
2. "Have you set up analytics" — answer fully in her control this week.

The deliverable is a sentence she can defend under follow-up, not a dashboard.

## Status Quo

Measured live during the session, not estimated:

```
GET https://sente-server.melaniesigrid.workers.dev/api/stats
  -> {"players":1,"online":0,"seeking":0}
GET .../api/ladder
  -> []
```

One registered handle. Nobody online. Empty ladder.

`GET /api/stats` already exists, public and unauthenticated, implemented at `server/registry.js:585-589` by counting Durable Object storage keys under the `player:` and `seek:` prefixes plus the live WebSocket count. So the "how many users" question is already answerable first-party, today, with one curl. What does not exist anywhere is **history**: nothing is retained, so "growing or flat" is unanswerable.

Today's workaround is therefore "I do not know," which is the thing that stings in an interview.

## Target User and Narrowest Wedge

**The human:** an interviewing engineering manager, in a room, asking a question she has been asked repeatedly. Secondarily an early investor. Tertiarily, per her own correction to P1, herself.

**The wedge:** the answer to question 2 above. A daily aggregate count kept on her own server, a public **route** serving the series, and one added sentence in a privacy notice that does not have to be retracted. Shippable in two to three days, and it converts the weakest signal she has (one user) into the strongest one she has (demonstrable judgment about measurement). The public *page* over that route is slice 2, deliberately.

## Premises

Agreed, with P1 and P3 revised during the session.

1. **(revised, on the builder's pushback)** There are two consumers, not one: an interviewer asking "how many," and the builder asking "what do players do." The second is unanswerable at n=1, but the instrument must exist **before** the first cohort arrives or that cohort's behaviour is lost permanently. You only get your first fifty players once.
2. The count is already answerable first-party via `/api/stats`. What is genuinely missing is **history**, not counting.
3. **(revised, after cross-model challenge)** The line is not browser-versus-server. Counting **page views** breaks `legal.js:187` wherever it runs. Any third-party script breaks it twice over. Counting **games and accounts** server-side does not break it at all. Rejected alternatives: the subagent's "any first-party counting is fine, rewrite the notice," and the original blunt "nothing in a browser, full stop."
4. In an interview, judgment outranks usage evidence. The notice plus a real test is a stronger artifact than a dashboard reading 1. The bottleneck is invitation, not measurement.

**Supporting research.** Reviewers weigh side projects, in descending order: judgment in picking a scoped real problem; whether it runs at a live URL; README and commit history; and only then evidence that someone used it. Usage is fourth and last, and Joseki is already strong on the first three.

**Why the privacy-first escape hatch does not apply.** Plausible, Fathom, Umami and Simple Analytics are cookie-free and generally avoid consent banners, which makes them the mainstream answer for this situation. They are still scripts, and they still count visits. The sentence at `legal.js:187` rules out the entire category, not just Google. That was a stronger commitment than the market's, and it is the asset.

## Recommended Approach

**B, sequenced.** Chosen by the builder over undifferentiated B, and it is the better answer: it puts invitation before day four so the build cannot become the reason the invitation slips.

### Slice 1, this week (Approach A, complete)

**Durability first.** Counters must be written to storage at each increment, not held in memory. A Durable Object is evicted after a short idle period, and at one registered player eviction between midnights is the normal case, not the edge. An in-memory counter would make `alarm()` wake a fresh instance and seal a row of zeros, which defeats the whole feature. The class is `new_sqlite_classes`, so per-increment writes are cheap local ones.

- Working key `day:YYYY-MM-DD`, the date computed in **UTC at each increment**, read-modify-write on each increment, with an in-memory copy kept only as a read cache and rehydrated in the existing `blockConcurrencyWhile` at `registry.js:60`.
- `alarm()` at 00:05 UTC seals **the previous day's** key, `day:<yesterday>`, into `stats:day:<yesterday>` and deletes it. It must not seal "today": increments between 00:00 and 00:05 already belong to the new day, and a late or retried alarm would otherwise fold the new day's first minutes into yesterday's row.
- `peakOnline` is a **stored running max**, not a cached one. Registry uses hibernatable sockets (`acceptWebSocket`, `webSocketClose` at `registry.js:626`), so a close sample can land on a fresh instance with no memory of the day's peak.

**Record shape.** Aggregate only, no per-person field, no page views:

```
{ date, accounts, newAccounts, gamesStarted, gamesFinished, peakOnline }
```

`botGames` and `humanGames` were in an earlier draft and are **cut**: house players run KataGo in the browser and never reach the Worker, so every server room is two registered humans. Those fields would be structurally 0 and equal-to-`gamesStarted` forever. Bot-game counts are obtainable only from the slice-2 local ring, which never leaves the device and therefore can never be aggregated. That is a real cost of the privacy stance and it is stated rather than hidden.

**Call sites, named.**

- `newAccounts`: **`register` (`registry.js:94`) only.** `signUp` (`registry.js:168`) delegates to it at `registry.js:173`, so incrementing in both double counts every signup. This is the same trap as `noteGame` below, in a second place.
- `gamesStarted` and `gamesFinished`: both flow through the single `noteGame` (`registry.js:514`), which `Room` calls for creation (`roomObject.js:35`) and for finish (`roomObject.js:96`) with the same signature. A naive increment double counts. Discriminate on the summary's `endedAt`/`result`.
- `accounts` is a **level, not a counter**: computed at alarm time from `storage.list({prefix:"player:"})`, so it self-corrects when `DELETE /api/me` or the admin removal runs. `newAccounts` is a flow and historical rows are never rewritten; a player who leaves is not retroactively un-joined. Note `storage.list` caps at 1000 keys by default, so pass an explicit limit or page it; otherwise the level silently plateaus at 1000. The same cap already applies to today's `stats()` at `registry.js:585`.
- **Accepted seam.** The `accounts` level is snapshotted at alarm time (00:05 UTC on day D) but written into day D-1's row, so a handle registered in the first five minutes of D lands in D-1's `accounts` and in D's `newAccounts`. `accounts[d] - accounts[d-1]` therefore will not always equal `newAccounts[d]`. Accepted rather than engineered around: the fix is a second snapshot path, and the error is one registration inside a five-minute window. Stated here so nobody later files it as a bug.
- `peakOnline`: max of `ctx.getWebSockets().length`, sampled at socket open and close only. These are authenticated lobby sockets, not page loads, so this is a count of players present, not visitors. That is the reason it does not cross the P3 line, and it is the field nearest the boundary, so it gets its own sentence in DECISIONS.md.

**Alarm mechanics.**

- A Durable Object has exactly one alarm and `setAlarm` overwrites. `Registry` has none today, so slice 1 is safe, but the next feature to want one would silently cancel the rollup. **Do not build a scheduler for this.** A generic schedule map is spec-work for a second consumer that does not exist, inside the slice this document insists must not slip. A comment on the single `setAlarm` naming the hazard buys the same protection at zero cost; build the dispatcher when something actually contends for the alarm.
- `alarm()` re-arms itself for the next 00:05 on **every** run, including the caught-error path. An uncaught throw retries; a caught and swallowed one would stop the clock permanently.
- The alarm writes a row every day, zeros included, so a quiet day is a zero row and not a gap in the series.
- **It also prunes.** Retention is 365 days and the privacy sentence will say so, therefore `alarm()` deletes `stats:day:` rows older than that on every run. A promised window the code does not enforce is exactly the failure the governing rule forbids.
- There is no deploy-time hook: `wrangler deploy` does not instantiate a DO. The first request after deploy arms the alarm. Arm it **inside the `blockConcurrencyWhile` at `registry.js:60`, after `#migrate` returns, unconditionally** (`if (!await storage.getAlarm()) setAlarm(...)`). Not inside `#migrate` itself: that returns early at `registry.js:66` for any object already at SCHEMA 3, which the production Registry is, so an arm placed there would be dead code.

**Route**, declared in `server/index.js` alongside `/api/stats` at `index.js:246`, with its line added to the route-table comment at `index.js:35`, reusing the `json()` and `CORS` helpers from `server/http.js`. `GET /api/stats/history?days=90`, public, unauthenticated. `days` clamped to 1..365, served from an in-memory cached array rather than a `storage.list` per request. The cache is rebuilt from storage on first request after eviction (lazily, not in the constructor) and invalidated by `alarm()` when it appends or prunes. Retention is **365 days**, decided, and that number goes in the privacy sentence. `GET /api/stats` keeps its current shape and behaviour.

**Tests** (`server/registry.test.js` already exists): counter increments including both double-count traps (`noteGame`, and `signUp` delegating to `register`), day rotation across the 00:00-00:05 seam, re-arm on the caught-error path, rehydration after simulated eviction, the 365-day prune, `days` clamping, and the history route's shape.

**Amend `src/content/legal.js` per line 244:** one standalone sentence saying the server keeps daily totals of accounts and games for 365 days and that they contain no per-person record. It does **not** name a URL, because the page that would make a URL meaningful is slice 2 and the governing rule forbids prose describing behaviour the code does not have yet. Slice 2 adds the link in a second sentence. Two amendments, zero retractions, which is the whole claim. `legal.js:187` is not touched, because nothing here counts a visit. Moving `UPDATED` is required by the same edit.

**Known limitation, stated not hidden.** At small n the aggregate is not truly aggregate: `newAccounts: 1` on a date, combined with `createdAt` on the public player card, identifies the person. Today the only identifiable person is the builder. Revisit before the ladder has strangers on it; the mitigation is suppressing or rounding small counts, not removing the field.

### Separate PR, not slice 1: the origin scan

The build-output scan that would give `legal.test.js` real teeth is supply-chain hygiene, not analytics, and it is the hardest item in the set. Keeping it in slice 1 is what would make slice 1 slip past the invitation this document calls the point. Ship it on its own, shaped like this:

- Scan `index.html` for `<script src>` and `<link href>` pointing at a foreign origin, **skipping non-`http(s)` schemes**: `index.html:7` is a `data:image/svg+xml` favicon and a naive check would flag it. It is otherwise clean today, so this can run under plain `npm test` immediately.
- A `dist/` scan cannot: `src/` already contains `fonts.googleapis.com`, `github.com`, `badukmovies.com`, `homepages.cwi.nl` and `web.archive.org` as credits and library content, all of which land in the bundle as string literals, so a naive string scan red-lights the repo on day one. It also needs a build to have run, which `npm test` does not guarantee. Gate it behind an allowlist of known content origins and wire it into CI after `npm run build`.
